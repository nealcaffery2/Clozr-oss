# Migrations

Applied to your Supabase project (`<your-project-ref>`) in this order. They
are the record of what the database is; the project is the live copy. A few
files are comment-only no-ops in the open-source release (they held one
company's own data or a private integration); they keep their numbers so the
ledger order holds.

## Applying them

Nothing to remember: **merging to `main` applies whatever is new.** The
"Apply database migrations" workflow (`.github/workflows/migrations.yml`) runs
on every push to `main` that touches this folder and applies, in order, every
file not yet recorded in `public.applied_migrations` — the ledger the runner
keeps in the database itself. Each file runs in its own transaction with its
ledger row, so a failing migration leaves nothing behind, the run stops there,
and the Actions summary says which file and why.

Three other ways in, all the same runner (`app/scripts/migrate.mjs`):

| Want to… | Do this |
| --- | --- |
| See what is applied and what is pending | Actions → *Apply database migrations* → **Run workflow** → `status` (or `pnpm migrate:status` locally) |
| See what a run would apply, without applying | the same with `dry-run` (or `pnpm migrate:dry-run`) |
| Apply now, without waiting for a merge | the same with `apply` (or `pnpm migrate`) |
| Tell the ledger a file is already in the database | `pnpm migrate --mark 125_x.sql` (`--baseline` marks every unrecorded file; used once, when the ledger was introduced) |

Locally the runner needs one of `SUPABASE_DB_URL` (Dashboard → Connect →
Session pooler connection string; runs through `psql`, no time limit) or
`SUPABASE_ACCESS_TOKEN` (a personal access token; runs through the Management
API, which cuts a statement off after about a minute). The workflow uses the
same `SUPABASE_ACCESS_TOKEN` secret as the edge-function deploy, and
`SUPABASE_DB_URL` when that secret is set too.

Project-specific values live in Supabase Vault, not in these files. The cron
kicks and triggers that call edge functions read them; until they exist those
jobs do nothing. Create them once in the SQL editor:

```sql
select vault.create_secret('https://<your-project-ref>.supabase.co', 'clozr_project_url');
select vault.create_secret('<service role key>', 'clozr_service_role_key');
select vault.create_secret('https://your-app.example.com', 'clozr_app_url'); -- links in webhook payloads (41)
```

Writing one: name it `NNN_what_it_does.sql` with the next number (two files
with the same number run in name order and the runner says so); make it safe
to re-run (`create or replace`, `if not exists`, `on conflict`); keep a heavy
data backfill in batches, or on the DB URL path; a big index goes in a file
of its own as `create index concurrently if not exists` (the runner sees
CONCURRENTLY and runs that file outside a transaction: psql statement by
statement, the Management API one request per statement, cut by
`scripts/sql-split.mjs`; 227 is the example). Add the row below. A file is applied once — a later edit to it is flagged by `status`
but never re-run, so a correction is a new file.

The Supabase MCP (`.mcp.json`) can also run SQL from a Claude session, with two
quirks: anything it classes as destructive (`drop …`, `truncate`, writes to
the migrations table) waits for a confirmation a non-interactive session
cannot give and times out, and a statement is cut off after 60 seconds. Write
`create or replace trigger` rather than drop-and-create, and batch big
updates by id range. The runner above has neither problem.

Migration 10 matters: Supabase's default privileges grant EXECUTE on every new
function in `public` to `anon` and `authenticated`, and `REVOKE ... FROM PUBLIC`
does not remove those. Without it `ingest_apply(workspace_id, envelope)` was
reachable at `/rest/v1/rpc/ingest_apply` with only the publishable key, which
would have let anyone write into any workspace by guessing an id — bypassing the
API-key check entirely. Any new SECURITY DEFINER function needs the same
treatment.

Migration 14 is the same lesson as 10 from a different angle: revoking a
function from `anon` and `authenticated` does not help while `PUBLIC` still
holds the grant, because both roles inherit it. `handle_new_user` stayed
callable at `/rest/v1/rpc/handle_new_user` until `PUBLIC` was revoked too.

The SECURITY DEFINER functions still reachable by `authenticated` are meant to
be, and the security advisor will keep listing them: `is_workspace_member`,
`member_role` and `has_role` are the RLS helpers (they answer a question about
the caller and nothing else); `issue_ingest_key`, `set_ingest_secret`,
`ingest_replay` and `ensure_calendar_token` check `has_role(ws, 'owner',
'admin')` before doing anything (migration 23; rotation only, for the
calendar token); `audit_event` checks membership and writes one row.

Migration 23 also closed two real holes. `members_insert_self` let any
signed-in user insert themselves into any workspace with any role, because the
policy only checked `user_id = auth.uid()`. And Supabase's default grants gave
`anon` and `authenticated` TRUNCATE on every table, which RLS does not govern.
Both are gone, and default privileges are altered so a new table starts
without them. The full design is in `docs/security.md`.

## Never hand-write a row in `auth.users`

GoTrue scans `confirmation_token`, `recovery_token`, `email_change`,
`email_change_token_new`, `email_change_token_current`, `phone_change`,
`phone_change_token` and `reauthentication_token` into Go `string` values, which
cannot hold NULL. The columns are nullable in Postgres, so a row written by hand
passes every constraint and still poisons the table: GoTrue's duplicate check
runs over `auth.users` on *every* signup and sign-in, so one bad row returns

    Scan error on column index 3, name "confirmation_token":
    converting NULL to string is unsupported

as a 500 on `/signup` — and the UI shows "Database error finding user", which
reads like the account is missing rather than unreadable.

If a row has to be touched directly (setting a password, confirming an address
without SMTP), set every one of those columns to `''` — never leave them NULL,
and never insert a user without them. Rows GoTrue creates itself are fine.


## Migration 15: the rest of the CRM

Until this, only the tables the ingest door writes existed — sellers,
properties, buyers, vendors, communications. Everything else a screen rendered
came from the sample graph compiled into the bundle, which is why signing in
changed nothing about what you saw.

Two kinds of thing deliberately stayed out. Reference content — stage names,
rehab presets, exit templates, the TC checklist templates, the automation
palette — is product configuration, identical for every workspace, and lives in
the bundle. And the team roster is derived from `workspace_members` joined to
`profiles` rather than duplicated into a table of its own.

RLS is written as a loop over the eleven table names rather than twenty-two
hand-written policies: one rule, visibly the same everywhere, and no table can
be missed.

## Migration 16: an FK that exists for PostgREST

`workspace_members.user_id` and `profiles.id` both reference `auth.users`, but
nothing connected them to each other. PostgREST embeds along foreign keys, so
`workspace_members?select=user_id,profiles(full_name)` failed with PGRST200 —
the roster came back with no names, every rep rendered "Unassigned", and the
leaderboard was empty. Nothing in the browser said why.

The constraint is safe because `handle_new_user()` inserts the profile before
the membership, so a member always has a profile.

## Texting

Outbound texts go CLOZR → Talkr → Telnyx, and the browser talks to Talkr
directly: Talkr trusts this project's tokens (PARTNER_JWKS_URL on the Talkr
server) and links a rep by email, so a text is sent as the person who wrote it
and CLOZR stores no Talkr credential. Talkr owns the numbers, the carrier, the
suppression list and quiet hours; its refusals reach the toast in plain words
(`suppressed`, `quiet_hours`, `no_from_number`).

lib/talkr.ts is the wire. lib/sms.ts is the CRM half Talkr has no reason to
know about: merge fields ({{first_name}}, {{address}}, …) filled from the
CLOZR row, and the sent message written to `communications` keyed
`msg:<talkr message id>` so it shows on the record's timeline. Because that id
is the row's identity, a later delivery receipt for the same message updates
it instead of adding a second copy of the text (migration 29).

Calls and replies come the other way without a webhook. Talkr's outbound webhooks fan
out call, recording and disposition events only — there is no `message.*`
event to subscribe to — but the browser is already on Talkr's SSE stream for
the dialer. So when a thread or the call log changes, `syncTalkrToRecords`
(lib/talkr-sync.ts) copies them onto the records they belong to: texts both
directions keyed `msg:<id>`, calls keyed `call:<id>` with talk time and the
rep's disposition as the summary. Keying on Talkr's own ids makes it
idempotent and lets a status or a duration move in place. A number with no
CLOZR record behind it is skipped rather than turned into a lead.

Two things depend on those call rows and had nothing to read before: the
reporting screen's call counts and talk time, and the AI action plan built
from a lead's history.

That covers replies while someone has CLOZR open, and catches up whatever was
missed the next time it is. `talkr-webhook` already understands `message.sent`,
`message.delivered`, `message.failed` and `message.received` and keys them by
message id, so adding those to Talkr's `PUBLIC_WEBHOOK_EVENT_TYPES` fan-out
would make it immediate and independent of anyone having a tab open.

## Action plans

Building a plan and enrolling somebody both worked, and then nothing happened:
the enrolment row sat there and no step was ever carried out.

CLOZR has no scheduler, and texting authenticates as the signed-in rep, so
nothing can send by itself at 9am on Tuesday without a credential this app
deliberately does not hold. What it can do is put the work in front of the rep
at the right moment. Enrolling now turns each step into a task dated from its
delay, carrying the step's message with merge fields already filled in, and
assigned to whoever owns the lead. Opening a text or email step goes straight
to that record's composer with the message in the box, so the queued touch is
one read and one click from sent.

Enrolling the same person in the same plan twice is refused rather than
doubling the sequence — the check is on an active enrolment, not on the tasks,
because the tasks belong to the enrolment that made them.

What this is not: automatic sending. A step goes out when a person sends it.
Making it autonomous needs either a server-side sender (a credential CLOZR
does not want) or Talkr's own sequence engine, which already has quiet hours
and suppression built in and is the better home for it.
